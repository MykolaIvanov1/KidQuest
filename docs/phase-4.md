# Сповіщення та Firebase Cloud Messaging

Реалізовано Phase 9, пункти 051–053 ТЗ: внутрішню скриньку сповіщень, реєстрацію пристроїв і доставку push через Firebase Cloud Messaging. Сповіщення залишаються доступними у KidQuest, коли Firebase не налаштований або браузер не підтримує push. Права й дані обмежуються поточним користувачем; спільна сім’я не дає доступу до чужої скриньки.

## Події

| Подія                                                 | Одержувачі                         |
| ----------------------------------------------------- | ---------------------------------- |
| Створено активний квест                               | Активні діти сім’ї                 |
| Виконання надіслано на перевірку                      | Обидва активні батьківські акаунти |
| Виконання підтверджено, нараховано бали або відхилено | Дитина, яка виконувала квест       |
| Отримано нове досягнення                              | Дитина, яка отримала відзнаку      |
| Запитано нагороду                                     | Активні батьки сім’ї               |
| Нагороду підтверджено, відхилено або видано           | Дитина, яка її запитувала          |

Підтвердження та кількість нарахованих балів об’єднані в одному повідомленні. Чернетки квестів, неактивні та видалені користувачі/профілі не створюють зайвих сповіщень. Повторення квесту щодня зберігає раніше реалізовану логіку розкладу; автоматичні нагадування за таймером цим етапом не додаються.

Запис сповіщення та завдання доставки створюються всередині тієї самої PostgreSQL-транзакції, що й бізнес-подія. Якщо підтвердження або списання балів завершується помилкою, відповідне повідомлення також не зберігається. Унікальність `userId + eventKey` захищає від дублювання під час повторних або конкурентних запитів. Зовнішній виклик Firebase виконується після транзакції фоновим обробником.

Для кожного зареєстрованого пристрою створюється окрема доставка в `PushDelivery`. Черга зберігається після перезапуску backend; тимчасові помилки повторюються з відкладенням, невірні токени відкликаються. Обробник використовує оренду запису, щоб паралельні процеси не забирали ту саму спробу. Зміна акаунта на одному браузері оновлює власника токена та версію прив’язки, скасовує старі доставки. Вихід і вимкнення push відкликають прив’язку. Як і в інших системах push, збій між прийняттям повідомлення провайдером і записом результату може призвести до повторної доставки; стабільний ID повідомлення використовується як browser tag.

На екрані блокування push показує загальний текст «У вас нове сповіщення». Назви квестів, ім’я дитини, баланс і фото залишаються всередині авторизованого застосунку. Firebase отримує мінімальний data-only payload з ID повідомлення та дозволеним внутрішнім шляхом; власний service worker показує одне повідомлення без автоматичного дублювання SDK. За тимчасових збоїв передбачено до п’яти спроб із початковою затримкою 60 секунд і подальшим збільшенням інтервалу.

## API

Усі маршрути мають префікс `/api/v1`, bearer-авторизацію та валідацію. Небезпечні HTTP-методи потребують налаштованого `Origin`.

| Метод і маршрут                           | Результат                                                                        |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `GET /notifications?limit=20&cursor=UUID` | Власні повідомлення, загальна кількість непрочитаних і курсор наступної сторінки |
| `PATCH /notifications/:id/read`           | Позначення власного повідомлення прочитаним; повтор не змінює початкову дату     |
| `POST /notifications/read-all`            | Позначення власних непрочитаних повідомлень, `{updated}`                         |
| `GET /notifications/status`               | `{pushConfigured}` для конфігурації backend                                      |
| `POST /devices`                           | Реєстрація/оновлення токена `{token,name?}` для поточного акаунта                |
| `DELETE /devices/:id`                     | Відкликання власної прив’язки пристрою                                           |

`limit` — ціле число від 1 до 50, типово 20. Порядок скриньки: новіші спочатку, зі стабільним порівнянням ID при однакових датах. Чужі, відсутні й видалені повідомлення або курсори повертають 404. Відповідь пристрою містить ID, назву, платформу й останню активність; FCM-токен, власник та внутрішні поля черги у відповіді відсутні. Посилання повідомлень обмежені дозволеними внутрішніми сторінками KidQuest.

Після вичерпання внутрішніх повторів конкурентна транзакція може повернути `409 CONCURRENT_UPDATE`. Повтор того самого підтвердження з незмінними ID виконання та `operationId` є безпечним: бали, відзнаки та сповіщення не дублюються. Інтеграційний тест перевіряє як паралельне підтвердження, так і явний повтор після такого конфлікту.

Сторінки `/child/notifications` і `/parent/notifications` доступні з дзвіночка з лічильником непрочитаних. Можна прочитати окреме повідомлення, усі повідомлення та завантажити наступну сторінку. Push вмикається лише після явного натискання користувачем; відмова браузера має зрозумілий стан. Передбачені світла/темна теми, завантаження, помилка з повторним запитом і порожня скринька.

Firebase SDK збирається локально в єдиний `/sw.js`: у production він також кешує публічну оболонку PWA, а в режимі розробки не кешує змінні Vite-модулі. Реєстрація push очікує активації нового worker, навіть якщо попередня версія оболонки ще активна. Оновлення зберігає попередній кеш публічних ресурсів для відкритих вкладок; офлайн-навігація використовує поточну оболонку. Авторизовані API-відповіді в цей кеш не потрапляють.

## Налаштування Firebase на Windows

Для поточного мобільного стенда використовуйте [покрокове налаштування Firebase](firebase-setup.md): воно готує окремі ігноровані файли командами `pnpm setup:firebase` і підключає їх через `pnpm mobile:firebase`, зберігаючи тунель та дані. Наведене нижче ручне редагування кореневого `.env` стосується локального `pnpm dev`; воно не вмикає FCM на ізольованому мобільному стенді.

Потрібен власний Firebase-проєкт із Web App та Cloud Messaging. Backend використовує приватний service account, frontend — публічну конфігурацію цього самого проєкту. Порядок отримання JSON-ключа наведено в [офіційній інструкції Firebase Admin SDK](https://firebase.google.com/docs/admin/setup). JSON-ключ і значення `private_key` зберігайте поза Git; вони потрібні тільки backend.

У кореневому локальному `.env` заповніть серверні значення з JSON service account:

```dotenv
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_CLIENT_EMAIL=firebase-adminsdk-example@your-project-id.iam.gserviceaccount.com
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nREPLACE_LOCALLY\n-----END PRIVATE KEY-----\n"
```

Усі три серверні значення задаються разом. Без них внутрішня скринька працює, а відправлення FCM вимкнене. Для цієї реалізації потрібно передати три поля service account у `.env`; саме лише встановлення `GOOGLE_APPLICATION_CREDENTIALS` не замінює їх.

У Firebase Console відкрийте Project settings → General → Your apps і скопіюйте публічну Web-конфігурацію. У Project settings → Cloud Messaging → Web Push certificates згенеруйте пару VAPID та скопіюйте її **публічний** ключ. Налаштування HTTPS, Web App і VAPID описані в [офіційному посібнику FCM Web](https://firebase.google.com/docs/cloud-messaging/web/get-started).

```dotenv
VITE_FIREBASE_API_KEY=your-web-api-key
VITE_FIREBASE_PROJECT_ID=your-project-id
VITE_FIREBASE_MESSAGING_SENDER_ID=your-sender-id
VITE_FIREBASE_APP_ID=your-web-app-id
VITE_FIREBASE_VAPID_KEY=your-public-vapid-key
```

У `VITE_*` не додавайте service account JSON, приватний ключ або серверні секрети: ці значення потрапляють у браузерну збірку. Після зміни `.env` перезапустіть застосунок; production frontend потрібно зібрати повторно.

У PowerShell з кореня KidQuest:

```powershell
pnpm install
pnpm db:generate
pnpm db:deploy
pnpm dev
```

Після входу відкрийте «Сповіщення», натисніть увімкнення push і дозвольте їх у браузері. На активній сторінці повідомлення оновлює скриньку та лічильник; у фоні service worker показує загальне системне повідомлення. Для перевірки: дитина надсилає квест, батьки отримують повідомлення; батьки підтверджують — дитина бачить підтвердження з балами у своїй скриньці. Перевіряйте відкриту сторінку, фоновий режим, перезапуск backend, вихід і повторний вхід іншим акаунтом.

## Телефон і межі перевірки

Для телефону потрібна HTTPS-адреса застосунку й API, доступна самому телефону, а також належний `FRONTEND_URL`. Комп’ютерний `localhost` з телефона вказує на сам телефон. Звичайна HTTP-адреса локальної мережі не є придатною основою для Web Push: FCM Web покладається на захищений контекст і service worker. Поведінка активної сторінки та фонової доставки описана в [документації отримання FCM](https://firebase.google.com/docs/cloud-messaging/web/receive-messages).

На iPhone/iPad із iOS/iPadOS 16.4 або новішою потрібно додати KidQuest на головний екран, відкрити з іконки та натиснути кнопку увімкнення push. Дозвіл запитується після дії користувача. Це вимога платформи, описана [командою WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/); фактична доступність також залежить від браузера та системних налаштувань.

Станом на 27.10.2026 користувач підтвердив встановлення й роботу KidQuest на Android та iPhone, а також офлайн-виконання з подальшою синхронізацією. Цей результат не підтверджує доставку через мережу FCM або показ на екрані блокування: Firebase-конфігурацію та системні push ще потрібно перевірити окремо. Автоматичні перевірки використовують окрему тестову PostgreSQL-базу й підмінений транспорт. Профіль і керування акаунтами описані у [phase-5.md](phase-5.md), офлайн-черга виконань і фото — у [phase-6.md](phase-6.md), локальний Квестик без зовнішнього провайдера — у [phase-7.md](phase-7.md).

## Перевірки

Команди загальної перевірки: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm db:test`, `pnpm build`.

Окремо успішно пройдено **26 інтеграційних тестів** у `backend/tests/notifications.integration.test.ts`. Вони працюють тільки з `DATABASE_TEST_URL` і перевіряють:

- авторизацію, ізоляцію скриньок між користувачами та сім’ями, приховані записи, курсори, валідацію й безпечні внутрішні посилання;
- читання повідомлень, одержувачів подій, повторні та конкурентні запити без дублікатів;
- реєстрацію пристроїв, конкурентну прив’язку одного токена, зміну власника та відкликання;
- відкат підтвердження, нарахування/списання балів, досягнень, повідомлень і вже записаних завдань доставки при помилці транзакції;
- розподіл доставок між незалежними обробниками, повтор після перезапуску, невірні токени, зміну власника під час надсилання, відновлення простроченої оренди та завершення після п’яти спроб.

Команда для цього набору: `pnpm --filter @kidquest/backend exec vitest run tests/notifications.integration.test.ts`. Перевірки використовують реальну PostgreSQL і підмінений транспорт, тому не підтверджують доступність зовнішньої мережі FCM.

Підсумок 23 жовтня 2026 року: **274 тести пройдено** — 42 спільної валідації, 147 backend та 85 frontend. У цьому етапі додано 22 серверні unit-тести, 26 інтеграційних тестів сповіщень і 30 frontend-тестів. Пройдено `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm build`, Prisma validate та **10 перевірок обмежень PostgreSQL**. Тестовий setup за замовчуванням обмежує пул кожного Prisma-клієнта чотирма з’єднаннями; явно заданий `connection_limit` у `DATABASE_TEST_URL` має пріоритет. Робочий `DATABASE_URL` не змінюється.

У браузері перевірено окремі скриньки обох ролей, читання повідомлень зі зміною лічильника 5 → 4 → 0, перехід до відповідного розділу, зміну акаунта та нове повідомлення дитині після видачі нагороди. Світлу й темну теми та ширину 320 px перевірено без горизонтального переповнення. Використано окрему тестову сім’ю; реальні сімейні дані не використовувались як fixtures.

Основні файли: `backend/src/modules/notifications/`, інтеграція подій у модулях tasks, task-completions, reward-requests і gamification; `frontend/src/features/notifications/`, `frontend/src/pages/NotificationsPage.tsx`, `frontend/src/service-worker/push.js`, `frontend/src/services/service-worker.ts`, `frontend/public/sw.js` та `frontend/vite.config.ts`; спільні DTO в `packages/types`, `.env.example` і міграція `prisma/migrations/20261024000000_notifications_outbox/`.
