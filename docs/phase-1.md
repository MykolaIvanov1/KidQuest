# Перший етап: основа KidQuest

## Узгоджений обсяг

Цей етап відповідає поточному запиту користувача з десяти пунктів. Він ширший за окремий Task 001 у прикладі промпту наприкінці ТЗ: поточний запит прямо включає PostgreSQL-схему, авторизацію та базовий інтерфейс. Файл технічного завдання збережено без змін.

`frontend/` і `backend/` — назви із поточного запиту замість `apps/web/` і `apps/api/`. Інші принципи архітектури ТЗ збережено: pnpm monorepo, спільні типи та валідація, ізольований доступ до даних, бізнес-правила на backend.

## Поведінка першого етапу

- Реєстрація першого з батьків створює нову сім'ю атомарно.
- Батьківська панель дозволяє створити дитячий акаунт або акаунт другого з батьків у своїй сім'ї.
- Обидві ролі входять через email і пароль. Паролі зберігаються як bcrypt-хеші.
- Access JWT перевіряється на backend; refresh-сесії зберігаються як хеші з ротацією та відкликанням.
- Роль і сім'я визначаються авторизованим користувачем, із перевіркою активності та soft delete.
- Початкові українські панелі відображають дані API та коректні порожні стани для нової сім'ї.
- Схема PostgreSQL підтримує кількох дітей, тоді як перший UI орієнтований на одну дитину.
- Світла й темна теми використовують CSS design tokens; керування доступне з клавіатури й враховує reduced motion.

Статистику, для якої ще немає реалізованого бізнес-процесу, не слід сприймати як завершену гейміфікацію. Таблиці квестів, нагород, досягнень і сповіщень створено як основу наступних модулів.

## API першого етапу

База URL: `/api/v1`. Відповіді використовують формат `success/data` або `success/error` із ТЗ.

| Метод | Шлях              | Доступ                                |
| ----- | ----------------- | ------------------------------------- |
| GET   | `/health`         | Перевірка доступності API             |
| POST  | `/auth/register`  | Реєстрація першого з батьків і сім'ї  |
| POST  | `/auth/login`     | Вхід обох ролей                       |
| POST  | `/auth/refresh`   | Оновлення сесії через HttpOnly cookie |
| POST  | `/auth/logout`    | Відкликання refresh-сесії             |
| GET   | `/me`             | Авторизований користувач              |
| GET   | `/family/members` | Батьки своєї сім'ї                    |
| POST  | `/family/members` | Батьки своєї сім'ї                    |
| GET   | `/statistics`     | Панель відповідно до ролі та сім'ї    |

Для захищених GET і створення учасника потрібний `Authorization: Bearer <access-token>`. Запити, що змінюють стан, потребують заголовка `Origin`, який точно відповідає origin із `FRONTEND_URL`; браузер додає його автоматично. Access token зберігається в пам'яті браузера; refresh token передається тільки через HttpOnly cookie, а в БД зберігається його хеш.

## Наступний етап

1. Категорії й CRUD квестів, щоденні виконання та soft delete.
2. Відправлення виконання дитиною, перевірка батьками, відхилення.
3. Фото: перевірка типу/розміру, оптимізація, окреме сховище.
4. Атомарне підтвердження виконання та одноразове нарахування балів у ledger.
5. CRUD нагород, запити, підтвердження, перевірка достатності балів і транзакційне списання.
6. Інтеграційні та E2E-перевірки повного сімейного сценарію.

Наступні окремі роботи за ТЗ: streak із часовою зоною, досягнення, календар і графіки, керування email/паролем та журнал входів у UI, FCM, Dexie/IndexedDB і черга синхронізації з idempotency, AI-модуль Квестика, production deployment і фінальне QA.

## Перевірки

Підсумковий прогін `pnpm test`: 46 із 46 тестів пройшли. `pnpm db:test`: 5 із 5 перевірок обмежень PostgreSQL пройшли. Команди перевірок наведено в кореневому README.

Backend перевірено HTTP-тестами з in-memory адаптером і реальним PostgreSQL 17.6: реєстрація, вхід, ротація й відкликання refresh-сесій, RBAC, ізоляція сімей, soft delete, валідація та конкурентне створення другого батьківського акаунта. Тести з PostgreSQL запускаються лише проти окремої тестової бази, а не проти даних користувача.

Frontend-тести перевіряють українські форми входу й реєстрації, локальну валідацію, перенаправлення за роллю, панелі з даними API та додавання учасника сім'ї. Окремі тести API-клієнта перевіряють спільний запит refresh для конкурентних викликів, повтор запиту після оновлення токена, завершення сесії після відмови refresh та українське повідомлення при втраті мережі.

Початкову міграцію застосовано до порожньої PostgreSQL-бази. Окремо перевірено обмеження сімейних зв'язків, повторних операцій і незмінюваного журналу балів; seed виконано двічі для перевірки повторного запуску без дублювання. Docker Compose не запускався в середовищі розробки через відсутність Docker; для перевірок використано ізольований локальний PostgreSQL.

У браузері з реальною API та БД перевірено реєстрацію батьківського акаунта, створення дитячого акаунта, вихід, вхід дитини та відновлення сесії після перезавантаження сторінки. Перевірено світлу й темну теми.

Production build формує список попереднього кешування PWA-оболонки. Фактичне встановлення PWA на телефон і поведінка оболонки без мережі ще потребують браузерної перевірки; наявність manifest і service worker не означає, що ці сценарії вже підтверджені. Повна робота з квестами офлайн та синхронізація черги не входять до цього етапу.
