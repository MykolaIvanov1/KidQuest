# Ручна резервна копія PostgreSQL і приватних фото

Скрипт `scripts/backup.mjs` виконує просте ручне резервне копіювання відповідно до розділу 47 ТЗ: custom archive `pg_dump`, копія приватного каталогу фото та `manifest.json` із SHA256 і розмірами. Планувальника, автоматичного очищення й автоматичного відновлення немає. PowerShell-обгортка: `scripts/backup.ps1`.

## Узгоджена копія

Перед початком зупиніть **усі процеси, що записують дані**: API, його обробник сповіщень, окремі worker, міграції та ручні зміни. PostgreSQL залиште запущеним. Не відновлюйте записи до успішного завершення копії. Сам `pg_dump` має узгоджений знімок БД, але узгодженість цього знімка з окремими файлами фото потребує зупинки записів на весь час копіювання.

Параметр `--writes-paused` підтверджує виконання цієї умови; локальний режим не зупиняє й не перевіряє ваші процеси. Compose-режим додатково перевіряє, що контейнер `api` існує та має стан `exited`; працюючий, перезапусканий, призупинений або відсутній контейнер не приймається. Відповідальність за інші джерела запису залишається в оператора.

Копія містить сімейні дані, хеші паролів, сесії та приватні фото. Каталог `.local/` і `.env*` ігноруються Git. Доступ до готових копій обмежте власним обліковим записом; переносьте їх у захищене сховище окремо від диска сервера. SHA256 перевіряє цілісність, але не шифрує файли й не захищає від одночасної навмисної підміни файлів та маніфесту.

## Локальний PostgreSQL на Windows

Запускайте з кореня KidQuest після зупинки власного API/worker у відповідному терміналі. Потрібні `pg_dump` і `pg_restore`; для сервера PostgreSQL 17 використовуйте клієнтські утиліти 17. На цій машині вони встановлені в `C:\Program Files\PostgreSQL\17\bin`.

```powershell
node -- scripts/backup.mjs --mode local --writes-paused --env-file .env --database-env DATABASE_URL --pg-bin 'C:\Program Files\PostgreSQL\17\bin' --storage ./storage --output .local/backups
```

Еквівалент через PowerShell:

```powershell
./scripts/backup.ps1 -Mode local -WritesPaused -EnvFile .env -DatabaseEnv DATABASE_URL -PgBin 'C:\Program Files\PostgreSQL\17\bin' -Storage ./storage -Output .local/backups
```

`node --` відокремлює параметри скрипту від параметрів Node.js: зокрема, Node 22 може сам обробляти `--env-file`, якщо пропустити цей роздільник. PowerShell-обгортка вже його додає.

За замовчуванням використовуються `.env`, `DATABASE_URL`, `STORAGE_PATH` або `./storage` та `.local/backups`. Усі відносні шляхи рахуються від кореня проєкту. Уже задані змінні процесу мають пріоритет над env-файлом: перевірте їх, якщо працюєте з кількома середовищами. `--database-env` дозволяє обрати іншу змінну, наприклад окрему тестову базу.

Якщо в БД дійсно ще немає фото й каталогу фото не існує, можна явно додати `--allow-empty-photos`. Для бази з фото цей параметр не використовуйте. Звичайний порожній каталог підтримується без додаткового прапорця. Скрипт очікує в каталозі тільки звичайні файли `UUID.webp`, створені KidQuest; вкладені каталоги, невідомі файли та посилання відхиляються. Каталог копій не може бути всередині каталогу вихідних фото.

Пароль і повна connection URL не передаються аргументами `pg_dump`/`pg_restore` та не друкуються. Локально підключення задається дочірньому процесу через змінні `PG*`; у Compose використовуються змінні контейнера. З URL передаються параметри TLS `sslmode`, `sslrootcert`, `sslcert`, `sslkey` і `target_session_attrs`; параметри пулу й `schema` Prisma до libpq не передаються. Архів містить **усю вибрану БД**, а не тільки схему із Prisma URL. Зберігайте env-файли приватно; не вставляйте URL або пароль у командний рядок.

## Production через Docker Compose

Потрібні налаштовані `.env.production`, Docker і запущений сервіс `db`. Цей приклад припускає, що API вже було створено й запущено відповідно до production-інструкції.

```powershell
docker compose --env-file .env.production -f docker-compose.prod.yml stop api
node -- scripts/backup.mjs --mode compose --env-file .env.production --compose-file docker-compose.prod.yml --writes-paused --output .local/backups
```

Скрипт викликає `pg_dump` усередині `db`, перевіряє читабельність архіву через `pg_restore --list` та копіює `/app/storage` зі зупиненого контейнера `api`. Локальні `--pg-bin`, `--storage`, `--database-env` і `--allow-empty-photos` у цьому режимі не приймаються. Команди не видаляють контейнери чи volumes.

Після успішного створення й перевірки копії поверніть API до роботи:

```powershell
docker compose --env-file .env.production -f docker-compose.prod.yml start api
```

При помилці `.incomplete` залишається, копія не вважається придатною. З'ясуйте причину та зробіть нову копію під час зупинених записів. Рішення про відновлення роботи сервісів після невдалої спроби приймайте явно, зберігши попередню готову копію.

## Результат і перевірка без БД

Кожний запуск створює **новий** каталог з UTC-часом і випадковим суфіксом:

```text
.local/backups/20261024T072152Z-0b8cd37e/
  database.dump
  photos/
    <uuid>.webp
  manifest.json
```

`manifest.json` записується після завершення дампу й копіювання; містить час, режим, версію `pg_dump`, кількість фото, шлях, розмір і SHA256 кожного файлу. Успішний запуск перевіряє маніфест, відсутність `.incomplete`, відсутність зайвих файлів, сигнатуру custom archive `PGDMP` та всі контрольні суми. Файли попередніх копій не перезаписуються й не видаляються.

```powershell
node -- scripts/backup.mjs --verify '.local/backups/20261024T072152Z-0b8cd37e'
# Або:
./scripts/backup.ps1 -Verify '.local/backups/20261024T072152Z-0b8cd37e'
```

Підставте фактичний каталог із повідомлення успішного запуску. Режим `--verify` не читає env-файл, не запускає Docker/PostgreSQL і працює без мережі. Він не замінює пробне відновлення: збережіть результат такого відновлення до використання копії для аварійного повернення сервісу.

## Пробне ручне відновлення в нове порожнє середовище

Нижче тільки явні ручні команди. Вони створюють **нову БД** і **новий порожній каталог фото**. Не підставляйте чинну БД чи робочий `STORAGE_PATH`; не застосовуйте `--clean` або `dropdb`. Копія БД і фото мають бути з одного завершеного каталогу. Для проби не запускайте звичайні API/worker проти цільової БД.

1. Перевірте готову копію через `--verify`. Вкажіть власні адресу PostgreSQL, порт і роль із правом створити нову БД. Пароль вводиться приховано та потрібний тільки на час команд. Назву нової БД змініть, якщо вона вже існує.

   ```powershell
   $pgBin = 'C:\Program Files\PostgreSQL\17\bin'
   $backup = (Resolve-Path -LiteralPath '.local/backups/20261024T072152Z-0b8cd37e').Path
   node -- scripts/backup.mjs --verify $backup
   if ($LASTEXITCODE -ne 0) { throw 'Перевірка копії не пройшла' }

   $env:PGHOST = '127.0.0.1'
   $env:PGPORT = '5432'
   $env:PGUSER = 'kidquest'
   $restoreDatabase = 'kidquest_restore_20261024'
   $restorePassword = Read-Host 'Пароль PostgreSQL' -AsSecureString
   $env:PGPASSWORD = [System.Net.NetworkCredential]::new('', $restorePassword).Password

   try {
     & (Join-Path $pgBin 'createdb.exe') --no-password --template=template0 $restoreDatabase
     if ($LASTEXITCODE -ne 0) { throw 'Нову БД не створено; відновлення зупинено' }

     & (Join-Path $pgBin 'pg_restore.exe') --no-password --no-owner --no-privileges --exit-on-error --single-transaction --dbname $restoreDatabase (Join-Path $backup 'database.dump')
     if ($LASTEXITCODE -ne 0) { throw 'Відновлення не пройшло; API не запускати' }
   } finally {
     Remove-Item Env:PGPASSWORD -ErrorAction SilentlyContinue
     $restorePassword = $null
   }
   ```

2. Створіть новий каталог фото. `File.Copy` із `false` забороняє перезапис. `New-Item` без `-Force` відмовиться, якщо кінцевий каталог уже існує. Вкажіть нову назву для кожної проби.

   ```powershell
   $restorePhotos = Join-Path (Get-Location) '.local/restore-20261024-photos'
   New-Item -ItemType Directory -Path $restorePhotos -ErrorAction Stop | Out-Null
   Get-ChildItem -LiteralPath (Join-Path $backup 'photos') -File | ForEach-Object {
     [System.IO.File]::Copy($_.FullName, (Join-Path $restorePhotos $_.Name), $false)
   }
   ```

3. Порівняйте кількість таблиць/міграцій і потрібні записи, кількість фото та їхні SHA256 із `manifest.json`. На окремому ізольованому backend перевірте вхід тестового акаунта, список квестів, журнал балів і відкриття фото з належною авторизацією. Для такої проби залиште Firebase-поля порожніми, щоб відновлена черга не надсилала реальні сповіщення; Квестик має працювати локально. Секрети `.env`, TLS-ключі та конфігурація Firebase в копію не входять — їх відновлюють із власного захищеного джерела.

При реальному аварійному відновленні перемикання робочого API на перевірені нові БД та каталог фото є окремою операцією з зупиненими записами. Скрипт резервної копії такого перемикання не виконує.

## Фактично перевірено 24 жовтня 2026 року

На PostgreSQL **17.6** у спеціально створених унікальних тестових БД пройшли 12 перевірок:

- створення нових порожніх джерела й цілі, застосування всіх справжніх Prisma-міграцій та двох синтетичних записів;
- два справжні `pg_dump` у різні каталоги без перезапису;
- `--verify` із недоступною адресою PostgreSQL, відсутніми env-файлом та `--pg-bin`: БД і клієнтські утиліти не потрібні;
- SHA256, розміри, завершений маніфест та побайтова відповідність одного синтетичного файла фото;
- справжній `pg_restore` у нову порожню БД: збіг кількості таблиць і завершених міграцій, усіх синтетичних записів; фото відновлено в новий порожній каталог зі збігом байтів;
- відхилення зміненого фото, зайвого файла, `.incomplete`, дубльованого запису маніфесту та файла з правильною контрольною сумою, але без формату `PGDMP`;
- відмова запуску без `--writes-paused`.

Артефакти цієї локальної перевірки збережені в ігнорованому `.local/backup-qa-20261024_352f04f3/result.json`. Це синтетичні fixtures; робочі сімейні БД, фото та процеси не змінювалися. **Compose-режим фактично не перевірено:** на цій машині недоступний runtime Docker/WSL. Його треба перевірити після налаштування Docker у власному окремому тестовому deployment.
