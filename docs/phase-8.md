# Етап 8: браузерні тести й підготовка експлуатації

Цей етап відповідає E2E/offline-перевіркам із розділу 44 та production/backup/documentation із розділів 45–48 і Phase 13–14 ТЗ. Квестик залишається локальним за погодженим рішенням. Нових користувацьких функцій поза ТЗ не додано.

## Що додано

- Playwright із двома профілями: Chromium/Pixel 7 і WebKit/iPhone 13, українською локаллю та часовою зоною Europe/Kyiv. Це емуляція браузера, не перевірка фізичного телефона.
- Повний сімейний сценарій через UI: реєстрація, створення дитини/категорії/квесту/нагороди, власний вхід дитини, фото, перевірка батьками, баланс і запит/підтвердження/видача нагороди. Перевіряються рольові переходи, точні суми й відсутність повторних транзакцій.
- Офлайн-сценарій: IndexedDB, фото й незмінний operationId після перезавантаження без мережі; першу успішну відповідь сервера навмисно втрачено, повтор створює рівно одне виконання й одне нарахування після перевірки.
- Ізольована E2E-БД, loopback-сервери, синтетичні фото та блокування зовнішніх мережевих запитів у браузері. Окремий тестовий HTTP-proxy розриває першу успішну відповідь виконання після справжнього commit API; це відтворює втрату відповіді в обох рушіях, зокрема коли WebKit не передає запит у browser route handler. Proxy й керування ним відсутні у production-образах. Firebase вимкнений у тестовій збірці. Кожний сценарій має нові процеси API/preview, тому швидкі тести не витрачають спільний IP-ліміт інших сценаріїв; серверні ліміти залишено без змін.
- Production Dockerfile і окремий Compose: PostgreSQL, одноразові міграції, API з користувачем node, Caddy зі SPA fallback/HTTPS, окремі volumes БД/фото/TLS, read-only filesystem для сервісів застосунку, readiness та обмежені журнали.
- `.env.production.example` і генератор локального production env з випадковими секретами без перезаписування наявного файла. Приватні значення не передаються frontend або Docker build context.
- Ручне узгоджене копіювання PostgreSQL і приватних фото, custom pg_dump, SHA256 manifest і перевірка копії. Справжнє відновлення перевірено на нових порожніх тестових БД/каталогах.
- Інструкції [сервера](production.md), [резервних копій](backup.md) і [QA Android/iPhone](mobile-qa.md).

## Помилки, знайдені браузерними тестами

Спільний `.env` містить `NODE_ENV=development` для API. Це значення впливало на Vite production build: React залишався в development, а `import.meta.env.PROD` вимикав автоматичний запуск оболонки Service Worker. `frontend/build.mjs` тепер явно задає production перед імпортом Vite; E2E використовує те саме значення.

Vite preview повертає `Vary: Origin`. Завантажені під час precache скрипти й запити ES modules мали різні Origin-заголовки, тому звичайний пошук не знаходив файли без мережі. Service Worker ігнорує Vary лише для дозволених публічних ресурсів того самого origin (`/assets/`, `/icons/`). API й приватні фото до Cache Storage не потрапляють. Семантика параметра описана в [CacheStorage.match](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage/match).

Після швидкого online reload свіжий знімок IndexedDB міг показувати старий баланс до завершення staleTime. Після підтвердження сесії AuthProvider тепер позначає відновлені запити неактуальними до відкриття приватного UI; відновлення без мережі зберігає кеш. Додано інтеграційну регресійну перевірку.

У Windows WebKit raw IndexedDB-перевірка незалежно від застосунку відтворила UnknownError під час запису Blob/File; ті самі байти успішно зберігалися як ArrayBuffer/Uint8Array. Нові фото тепер записуються як ArrayBuffer, підготовлений до початку IndexedDB-транзакції. Перед multipart-надсиланням із байтів відновлюється Blob. Старі Blob-записи підтримуються; перевірено читання, надсилання старого формату та відсутність часткового запису при помилці читання файла. Це виправлення сумісності не замінює фізичної перевірки Safari на iPhone.

Caddy застосовує `no-cache` до `index.html` після SPA rewrite, включно з прямими посиланнями на вкладені сторінки. Відсутній `/assets/*` повертає 404, а не HTML.

## Підготовка E2E на Windows

Потрібні встановлені залежності й працездатний локальний PostgreSQL. Створіть **нову окрему БД** `kidquest_e2e`, відмінну від робочої та інтеграційної. Наприклад, коли розробницька БД запущена через Compose:

```powershell
docker compose exec -T db sh -c 'exec createdb -U "$POSTGRES_USER" kidquest_e2e'
```

Для окремо встановленого PostgreSQL створіть базу через pgAdmin/createdb під власним користувачем. Помилка «already exists» не є приводом видаляти наявну БД: перевірте, що це саме тестова база, або оберіть іншу нову назву з `_e2e`.

Створіть ігнорований Git файл `.local/e2e-db.env`. Скопіюйте в нього власний локальний URL, змінивши лише назву бази на нову E2E-базу:

```dotenv
DATABASE_E2E_URL=postgresql://YOUR_USER:YOUR_URL_ENCODED_PASSWORD@127.0.0.1:5432/kidquest_e2e
```

Не змінюйте робочий DATABASE_URL для E2E. Міграції runner застосовує до тестового URL самостійно, seed не потрібний. Допускаються лише loopback-host та окрема назва з сегментом `e2e`; перевірка порівнює адресу/порт/назву з робочою й інтеграційною БД незалежно від облікових даних.

```powershell
pnpm test:e2e:install
pnpm test:e2e
```

Браузери завантажуються в ігнорований каталог `.local/playwright-browsers`. Тести запускають зібраний API на 4100 та production preview на 5180 і тестовий proxy на 4101; зайняті порти спричиняють помилку, наявні сервери не використовуються. Запускайте один E2E-прогін одночасно. Тестові сім’ї створюються з випадковими адресами `example.test` і залишаються в окремій E2E-базі; робочі записи не видаляються.

Окремий браузер або сценарій:

```powershell
pnpm test:e2e --project=chromium-android
pnpm test:e2e --project=webkit-iphone
pnpm test:e2e --project=chromium-android --grep=offline
```

HTML-звіти лежать у `playwright-report/<browser>/<scenario>/`, знімки й failure traces — у `test-results/`. Артефакти можуть містити тестові паролі, cookies і токени, тому ці каталоги ігноруються Git; їх не публікують.

## Перевірки

Успішно пройшли:

- **480 unit/integration**: 45 validation, 260 backend із реальною PostgreSQL та 175 frontend. Після зміни формату фото весь frontend-набір пройдено повторно.
- **4 E2E**: family flow й offline/reload/lost-response у Chromium/Pixel 7 та WebKit/iPhone 13. Обидва браузери зберегли одне фото/operationId після повністю офлайн-перезавантаження; два відправлення одного operationId дали рівно одне виконання й одну транзакцію після перевірки.
- **4 перевірки E2E-конфігурації**: окрема loopback-БД, заборона робочої/інтеграційної цілі, нормалізація URL та приховування помилкових секретних значень.
- **12 обмежень PostgreSQL**, усі fixtures відкочені.
- **12 перевірок backup/restore** зі справжніми pg_dump/pg_restore й синтетичним фото.
- TypeScript для всього monorepo/Prisma/E2E, ESLint, Prettier, git diff --check та production build.

Під час offline E2E повідомлення Vite `socket hang up` є очікуваним наслідком навмисно втраченої відповіді proxy; успішність визначається перевірками повтору й серверних записів. Rollup також виводить попередження щодо PURE-коментарів у встановленому Zod; збірка завершується успішно.

Окремо перевірено синтаксис Compose, native `caddy validate`, HTTP-поведінку статичних маршрутів Caddy та перенесення згенерованого Prisma client між різними фізичними шляхами pnpm. Це не замінює Linux image build/runtime.

## Перевірка Docker 26.10.2026

Після встановлення WSL 3.0.3 та Docker Engine 29.9.2 виконано справжню Linux/AMD64-збірку всіх трьох образів: API, web і migrate. API працює на Node.js 24.22.1 з UID 1000; root filesystem API/web read-only. Сервіси db/api/web отримали healthy, шість міграцій завершилися з кодом 0. API та PostgreSQL не публікували host-порти.

Для QA створено окремий project `kidquest-qa-20261026-72fb6fca` з новими volumes і випадковими тестовими секретами. Caddy використовував `tls internal` та єдиний опублікований порт `127.0.0.1:55443`. HTTPS-клієнт перевіряв сертифікат за експортованим публічним root.crt; системну довіру Windows і DNS не змінювали.

Пройшли **11 HTTPS-перевірок**: readiness, SPA/assets/SW/cache/security headers, Origin gate, Secure/HttpOnly/SameSite cookies та refresh rotation, батьківські/дитячі ролі, створення сім’ї/квесту/нагороди, справжнє PNG→WebP через Sharp, приватність фото, replay виконання/підтвердження, нарахування 40 один раз, списання 25 один раз та підсумковий баланс 15 із двома транзакціями.

Зупинений API не записував дані під час Compose backup. `pg_dump`, фото та manifest успішно створені й перевірені. У ще одному новому project `kidquest-restore-20261026-72fb6fca` архів відновлено в порожню БД і новий photo volume. Пройшли **9 перевірок відновлення**: UID 1000, шість міграцій, початкові IDs/стани, SHA256 фото, вхід і refresh, баланс/журнал, приватність фото, replay без дублів та запис/читання нового завантаженого фото. Права відновленого каталогу — UID 1000, mode 0700; додатковий chown не знадобився.

Практична перевірка виправила команду runbook: `compose create` не підтримує `--no-deps`; для створення зупиненого API використовується `compose up --no-start --no-deps --no-build --pull never api`. Для власного project name backup використовує `COMPOSE_PROJECT_NAME` із вибраного env-файла. Відновлювальний env залишає серверний Firebase вимкненим.

Обидва тестові deployment зупинені, їхні volumes та перевірений backup збережені. Звіти й синтетичні fixtures знаходяться в ігнорованому `.local/docker-qa-20261026-72fb6fca/`; секретні fixture/env не публікуються.

Локальний KidQuest з наявною сімейною БД знову запущено на http://localhost:5173; API — 4000, PostgreSQL — 56179. Робочий DATABASE_URL та сімейні дані не переносились до Docker.

## Що потребує зовнішнього середовища

Потрібні публічний сервер/домен з HTTPS і фізичні Android/iPhone для встановлення, холодного запуску PWA, поведінки мобільного сховища та дозволів камери/сповіщень. Перевірка локального TLS не підтверджує видачу публічного ACME-сертифіката. Push потребує Firebase та перевірки доставки на пристрої; локальний Квестик працює без зовнішніх ключів. Зовнішній AI-провайдер зараз не запланований за рішенням користувача. Сайт не опубліковано.
